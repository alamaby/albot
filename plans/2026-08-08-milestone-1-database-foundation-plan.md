# Milestone 1 Database Foundation Plan

Created: 2026-08-08 13:01:28

## Objective

Membangun database foundation yang versioned, aman, dapat diuji, dan siap dipakai oleh application layer tanpa schema drift. Milestone ini menghasilkan schema inti, strict RLS, minimal grants, atomic job/session operations, generated TypeScript types, hosted-development test harness, serta workflow migration development dan production.

Milestone 1 selesai hanya setelah migration yang sama dapat diterapkan secara idempotent ke hosted Supabase development, seluruh schema/security/concurrency assertions lulus, generated types bersih, dan tidak ada migration Milestone 1 yang dijalankan ke production.

## Scope

- Menambahkan struktur `supabase/` dan konfigurasi Supabase CLI untuk Database as Code.
- Membuat migration additive untuk seluruh core tables Milestone 1.
- Menetapkan status values, constraints, foreign keys, unique constraints, dan indexes.
- Mengaktifkan RLS pada seluruh exposed tables dan menghapus akses langsung `anon`/`authenticated` secara default.
- Menambahkan minimal grants untuk fungsi database yang memang perlu dipanggil server.
- Menambahkan atomic job claim function dengan lease ownership dan `FOR UPDATE SKIP LOCKED`.
- Menambahkan conditional prompt-session transition function untuk menolak stale state.
- Menghasilkan `src/server/supabase/database.types.ts` dari hosted development schema.
- Menambahkan schema, RLS/grant, function, idempotency, dan concurrency tests.
- Menambahkan workflow migration development dan production dengan GitHub Environment approval.
- Menambahkan migration/static SQL checks ke validation workflow.
- Mencatat evidence hosted development; production execution tetap di luar scope M1.

## Out Of Scope

- Menjalankan migration ke hosted Supabase production.
- Menulis repository application layer untuk semua tables.
- Membuat Telegram webhook, job processor HTTP endpoint, dispatcher, atau provider adapter.
- Menyimpan plaintext provider API key atau membuat encryption service; encryption masuk Milestone 2.
- Membuat admin UI/API.
- Menambahkan seed production atau data pengguna nyata.
- Membuat destructive migration, backfill data production, atau schema rollback otomatis.

## Architecture Decisions

### Database Delivery

- PostgreSQL/Supabase schema menjadi code dalam `supabase/migrations/`; dashboard SQL Editor bukan jalur normal schema changes.
- Setiap perubahan schema memakai migration baru. Migration yang sudah diterapkan tidak diedit.
- Migration M1 bersifat additive. Rollback operasional memakai forward-fix migration.
- Hosted Supabase development menjadi target integration test. Production hanya menerima workflow definition pada M1, bukan migration execution.
- `supabase db push` memakai database password secret dan project ref yang terikat GitHub Environment terkait.
- Workflow harus checkout exact commit, menggunakan pinned Supabase CLI version, tidak mencetak secret, dan menyimpan evidence non-sensitive.

### Schema Naming And Types

- Semua object aplikasi berada di schema `public` agar PostgREST/Supabase tooling tetap sederhana; akses dibatasi dengan RLS dan grants.
- Primary key menggunakan `uuid` dengan `gen_random_uuid()`.
- Timestamp menggunakan `timestamptz` dan default `now()` untuk creation timestamps.
- Telegram IDs menggunakan `bigint`; jangan cast ke JavaScript `number` pada application boundary karena dapat melampaui safe integer. Generated DB types tetap merepresentasikan nilai sesuai Supabase serializer.
- Flexible provider/job metadata memakai `jsonb` dengan default `'{}'::jsonb` dan constraint `jsonb_typeof(...) = 'object'`.
- Status/capability values memakai `text` + named `CHECK` constraints untuk perubahan additive yang lebih mudah daripada PostgreSQL enums. Risiko typo ditutup oleh constraints dan generated domain schemas pada milestone berikutnya.
- Constraint dan index diberi nama stabil agar schema assertions serta future migrations tidak bergantung pada nama autogenerated.

### Security Boundary

- Enable dan force RLS pada semua core tables yang terekspos melalui PostgREST.
- Revoke table privileges dari `anon` dan `authenticated`; tidak membuat permissive browser policies pada M1.
- Service role tetap server-only dan bypass RLS sesuai Supabase behavior.
- Fungsi internal tidak diberikan ke `anon`/`authenticated`; grant hanya ke `service_role` bila RPC diperlukan.
- Semua `security definer` functions memakai `set search_path = pg_catalog, public`, schema-qualified object references, input validation, dan explicit grants.
- `provider_keys.key_ciphertext`, `key_iv`, dan `key_auth_tag` hanya menyimpan ciphertext material. Migration/seed/test tidak boleh mengandung provider key asli.

### Concurrency

- Job claim memakai one-statement/transactional function dengan `FOR UPDATE SKIP LOCKED`.
- Claim hanya memilih job `queued`, due (`available_at <= now()`), belum melewati `max_attempts`, dan tidak memiliki live lease.
- Claim atomically mengisi `locked_at`, `locked_by`, meningkatkan `attempt_count`, dan mengubah status menjadi `processing`.
- Completion/retry functions bukan deliverable wajib M1; namun schema dan claim result harus membawa lock owner agar Milestone 3 dapat menerapkan conditional completion.
- Session transition memakai expected-state compare-and-set. Stale caller mendapat zero-row/false result dan tidak mengubah session.

## Core Schema

### `bot_users`

- Columns: `id`, `telegram_user_id`, `telegram_chat_id`, `username`, `is_allowed`, `is_admin`, `created_at`, `updated_at`, `last_seen_at`.
- Constraints: primary key; unique `telegram_user_id`; booleans non-null default false.
- Index: optional partial/covering index untuk allowlist lookup hanya jika query plan membutuhkannya; unique index sudah melayani lookup by Telegram user ID.
- Privacy: username optional dan tidak dipakai sebagai authorization identity.

### `provider_configs`

- Columns sesuai plan utama: capability, adapter type, endpoint/model/settings, selection policy, priority, weight, active/version timestamps.
- Checks:
  - `capability in ('reasoning', 'image_generation')`.
  - `selection_strategy in ('priority_failover', 'weighted')` atau subset V1 yang benar-benar dipakai.
  - `priority >= 0`, `weight > 0`, `config_version > 0`.
  - `settings` wajib JSON object.
- Index: `(capability, is_active, priority, id)` untuk deterministic selection.

### `provider_keys`

- Foreign key `provider_config_id` ke `provider_configs(id)` dengan delete behavior explicit; default `restrict` untuk mencegah accidental credential-history deletion.
- Unique `(provider_config_id, key_fingerprint)`.
- Checks: ciphertext/IV/auth tag/fingerprint non-empty, `weight > 0`, `failure_count >= 0`.
- Index: `(provider_config_id, is_active, cooldown_until, last_used_at, id)`.
- Plaintext key dilarang di schema, logs, fixtures, atau generated evidence.

### `prompt_sessions`

- Status allowlist: `received`, `enhancing`, `awaiting_confirmation`, `awaiting_revision_input`, `generating`, `result_ready`, `enhancement_failed`, `generation_failed`, `completed`, `cancelled`, `expired`.
- Checks: `expires_at > created_at`; `completed_at` hanya diperlukan untuk terminal completion sesuai transition rules, bukan enforced terlalu ketat sebelum flows stabil.
- Self-cycle avoidance: `active_revision_id` dan `active_generation_attempt_id` ditambahkan setelah child tables ada, atau foreign keys dibuat `DEFERRABLE`/via later migration step.
- Index: `(telegram_user_id, status, updated_at desc)` untuk active-session lookup; index expiry untuk cleanup bila query telah ditentukan.

### `prompt_revisions`

- Foreign key `session_id` ke `prompt_sessions(id)`.
- Unique `(session_id, revision_number)`; check `revision_number > 0`.
- Status allowlist minimal: `pending`, `processing`, `completed`, `failed`, `cancelled`.
- Source prompt non-empty; enhanced fields nullable sampai processing selesai.
- Foreign key reasoning provider config memakai `on delete restrict` atau `set null` berdasarkan audit requirement. Pilihan default M1: `on delete restrict`, karena configs tidak dihapus secara fisik.

### `generation_attempts`

- Foreign keys ke session dan revision; check bahwa attempt number positif.
- Unique `(session_id, attempt_number)`.
- Status allowlist minimal: `queued`, `processing`, `succeeded`, `failed`, `cancelled`.
- `parameters` wajib JSON object.
- Index pada `(session_id, status, created_at desc)` bila dipakai untuk active-generation guard.

### `jobs`

- Foreign keys optional ke session, revision, dan generation attempt.
- Status allowlist: `queued`, `processing`, `succeeded`, `retry_scheduled`, `failed`, `cancelled`.
- `attempt_count >= 0`, `max_attempts > 0`, `attempt_count <= max_attempts` bila retry semantics tidak membutuhkan temporary overflow.
- `payload` wajib JSON object; error text sudah redacted by contract.
- Index claim: `(status, available_at, created_at, id)` dengan partial predicate untuk claimable statuses jika query function identik.
- Index lease recovery: `(locked_at, id)` partial untuk processing rows.
- Lock consistency checks dibuat hanya bila tidak menghambat forward recovery; minimal memastikan `locked_by` dan `locked_at` sama-sama null atau sama-sama terisi.

### `provider_requests`

- Foreign keys ke jobs, provider configs, dan provider keys.
- Capability/status constraints.
- Checks: HTTP status antara 100–599 bila terisi; latency non-negative.
- Index `(provider_config_id, created_at desc)` dan optional `(job_id, created_at)`.
- Error message wajib redacted pada application boundary; DB tidak dapat membuktikan redaction, jadi test hanya memastikan field yang tersedia bernama `error_message_redacted`.

### `telegram_updates`

- Unique `update_id` sebagai deduplication boundary.
- `update_type` allowlist awal: `message`, `callback_query`.
- Index `received_at` untuk retention cleanup jika dibutuhkan.
- Raw update body tidak disimpan pada M1.

### `callback_events`

- Unique `callback_query_id`.
- Foreign key optional ke session.
- Action allowlist sesuai logical callback actions pada plan utama.
- Index `(session_id, received_at desc)`.

### `job_events`

- Foreign key ke jobs dan session; payload JSON object.
- Index `(session_id, created_at, id)` dan `(job_id, created_at, id)`.
- Payload tidak boleh berisi secrets; application-level redaction test masuk milestone pemakai, sedangkan M1 menyediakan schema boundary.

## Foreign Key And Delete Policy

- Default foreign keys memakai `on delete restrict` untuk config/audit records.
- Child lifecycle records yang tidak boleh orphaned memakai `on delete cascade` hanya bila parent deletion memang diizinkan. M1 memilih conservative `restrict` dan soft/terminal state; hard-delete flows belum dibuat.
- Cyclic active pointers pada `prompt_sessions` ditambahkan setelah child tables dan dibuat nullable.
- Foreign key indexes ditambahkan ketika PostgreSQL tidak membuatnya otomatis dan query/delete checks membutuhkan lookup efisien.

## Timestamp Strategy

- `created_at` default `now()` dan immutable by convention.
- `updated_at` default `now()` serta trigger reusable `set_updated_at()` hanya pada mutable tables: `bot_users`, `provider_configs`, `provider_keys`, `prompt_sessions`, dan `jobs`.
- Trigger function memakai `security invoker` default dan fixed `search_path` bila object resolution dibutuhkan.
- Append-only/event tables tidak memakai update trigger.

## RLS And Grants Matrix

| Object class | `anon` | `authenticated` | `service_role` | Notes |
|---|---|---|---|---|
| Core tables | No direct grants | No direct grants | Server access | RLS enabled + forced; no permissive browser policy in M1 |
| Provider key columns | No access | No access | Server only | Ciphertext remains sensitive operational data |
| Job claim function | No execute | No execute | Execute | `security definer`, fixed search path, validates worker ID |
| Session transition function | No execute | No execute | Execute | Expected-state compare-and-set |
| Schema metadata assertions | No app grant | No app grant | CI DB connection only | Tests run through CI credentials |

Security tests harus membedakan RLS denial dari empty-table false positive. Setiap tested table menerima disposable fixture via service role, lalu anon/authenticated read memastikan row tidak terlihat atau request ditolak. Cleanup memakai dedicated hosted development test data only.

## Atomic Function Contracts

### `claim_job`

Proposed signature:

```sql
public.claim_job(
  p_worker_id text,
  p_lease_timeout interval default interval '5 minutes'
)
returns setof public.jobs
```

Contract:

- Reject blank/oversized worker ID and non-positive lease timeout.
- Select one deterministic claimable row ordered by `available_at`, `created_at`, `id`.
- Use row locking with `FOR UPDATE SKIP LOCKED`.
- Treat expired processing lease as recoverable only if status/lease policy explicitly allows it.
- Atomically set `status = 'processing'`, lock owner/time, increment attempt count, and return claimed row.
- Return zero rows when nothing is claimable.
- Grant execute only to `service_role`.
- Concurrent test with at least two workers and one job must prove exactly one claim.

Risk: exposing `interval` from RPC can vary by client serialization. If Supabase RPC ergonomics prove awkward, use `p_lease_seconds integer` with bounded range. Decide during implementation after a minimal generated-client contract test.

### `transition_prompt_session`

Proposed signature:

```sql
public.transition_prompt_session(
  p_session_id uuid,
  p_expected_status text,
  p_new_status text,
  p_active_revision_id uuid default null,
  p_active_generation_attempt_id uuid default null
)
returns public.prompt_sessions
```

Contract:

- Validate expected/new status against same allowlist as table constraint.
- Update only `where id = p_session_id and status = p_expected_status`.
- Return updated row; return no row or explicit typed result for stale/missing state without mutating data.
- Update active pointers only when supplied; avoid accidentally clearing them on unrelated transitions.
- Set `completed_at` for terminal completion and maintain `updated_at`.
- Grant execute only to `service_role`.
- Contract test proves stale expected status cannot overwrite current state.

Risk: one generic transition function can permit invalid state edges despite valid status names. M1 must either encode an explicit transition matrix in SQL or limit function contract to compare-and-set while application state-machine validation lands before external use. Preferred: encode critical invalid terminal-state exits in SQL and keep full transition policy in application domain tests. Document any permitted-but-unused edges.

## Migration Workflows

### Development Workflow

- File: `.github/workflows/migrate-development.yml`.
- Trigger: `workflow_dispatch` with optional expected commit SHA; no automatic migration on every push.
- Job environment: GitHub Environment `development`, requiring reviewer approval.
- Secrets: development project ref, DB password/access token, API URL, service role key/publishable key only when integration tests need them.
- Steps:
  1. Checkout exact selected commit from `main` or approved ref.
  2. Setup Node 22 and install dependencies with `npm ci`.
  3. Install/pin Supabase CLI without globally floating `latest`.
  4. Link development project non-interactively.
  5. Show pending migration list without exposing connection secrets.
  6. Apply pending migrations to hosted development.
  7. Run migration command/list again to prove no pending duplicate application.
  8. Generate database TypeScript types from development project.
  9. Fail if generated output differs from committed `database.types.ts`.
  10. Run schema assertions, RLS/grant tests, service-role tests, and concurrency tests.
  11. Upload sanitized test/evidence artifact with commit SHA and migration version.
- Concurrency group serializes development migrations.
- Workflow timeout and least GitHub token permissions required.

### Production Workflow

- File: `.github/workflows/migrate-production.yml`.
- Trigger: manual dispatch, only from `main`.
- Job environment: GitHub Environment `production`, separate required reviewer.
- Guard requires exact commit/migration set evidence that passed development.
- Workflow definition includes preflight migration list, metadata capture, migration apply, and read-only smoke checks.
- **Do not execute this workflow during Milestone 1.** Acceptance requires no M1 migration applied to production.
- Add explicit confirmation input containing expected production project ref suffix or release identifier to reduce wrong-target risk.
- Concurrency group serializes production migrations.

### Validation Workflow

- Extend `.github/workflows/validate.yml` with:
  - Migration filename/order checks.
  - Forbidden destructive statement scan (`drop`, unsafe `alter`, `truncate`, broad grants) with documented allowlist mechanism.
  - SQL formatting/lint command using pinned tooling.
  - `test:contract` and static database type freshness check where hosted access is not required.
- Static scans are guardrails, not SQL semantic proof. Hosted integration tests remain mandatory before acceptance.

## Generated Type Strategy

- Generate from hosted development after migration, never hand-author full schema types.
- Commit output to `src/server/supabase/database.types.ts`.
- Add `npm` script that regenerates into temporary output or target file and checks Git diff in CI/workflow.
- Update `getSupabaseAdmin()` to return `SupabaseClient<Database>` after generated types exist.
- Avoid aliases that hide nullable/database-return semantics unless domain layer needs them.
- Gate: regenerate twice against unchanged schema; second run must create no diff.

## Test Strategy

### Static Migration Tests

- Migration filenames unique, timestamp-ordered, and immutable after application.
- No plaintext-like provider keys, service role keys, Telegram tokens, or production data.
- No forbidden destructive SQL in M1.
- Every exposed table has RLS enable/force statements.
- Security-definer functions include fixed `search_path` and explicit revoke/grant.

### Schema Assertions

- Assert all required tables, columns, types, nullability, defaults, primary keys, foreign keys, checks, unique constraints, triggers, functions, and indexes.
- Assert named constraints and function signatures to catch drift.
- Assert migration version recorded in Supabase migration history.
- Run against hosted development only.

### RLS And Grant Tests

- Insert disposable fixture rows via service role.
- Query each core table with anon/publishable credentials and verify no row exposure.
- If authenticated-client testing is configured, verify no direct access without explicit admin policy.
- Verify `anon`/`authenticated` cannot execute atomic functions.
- Verify service role can access required table/function path.
- Clean up only tagged test rows in hosted development.

### Atomicity Tests

- Insert one queued due job.
- Start at least two concurrent claim calls with distinct worker IDs.
- Assert one result contains job and all other results are empty.
- Assert persisted job has one owner, `processing` status, one attempt increment, and lock timestamp.
- Test no claim before `available_at`, no claim after max attempts, and expired lease recovery if implemented.
- Transition one session successfully, then call with stale expected state and assert no mutation.

### Type And Application Verification

- Generate DB types and assert clean Git diff.
- Run `npm run typecheck` and `npm run build` using generated types.
- Run existing unit tests to prevent Milestone 0 regression.

## Risks

- **Hosted-only development can affect shared test data.** Mitigation: dedicated development project, tagged disposable fixtures, serialized workflow, and cleanup. Limitation: it is still not as isolated as ephemeral local databases.
- **RLS tests can produce false confidence on empty tables.** Mitigation: insert known fixture with service role before testing anon/authenticated visibility.
- **Service role bypasses RLS.** Mitigation: never expose service-role key to browser; test grants and anon paths separately.
- **Generic state transition RPC may allow semantically invalid edges.** Mitigation: encode terminal-state protections and document application-level transition matrix before external use.
- **`FOR UPDATE SKIP LOCKED` tests may be flaky if concurrency is simulated sequentially.** Mitigation: use separate concurrent connections/promises and assert persisted owner, not only returned values.
- **Static destructive-SQL scans have false positives/negatives.** Mitigation: require migration review and hosted schema assertions; scanner remains a guardrail, not proof.
- **Generated types can drift if produced from wrong project.** Mitigation: workflow binds project ref to GitHub Environment and records non-secret ref/migration version.
- **Production workflow can target wrong project.** Mitigation: separate secrets, environment approval, main-only guard, explicit target confirmation, and no M1 execution.
- **Broad `security definer` functions increase privilege risk.** Mitigation: fixed search path, schema qualification, bounded inputs, public execute revoke, and service-role-only grant.
- **Text check constraints require migration for new status.** Benefit: safer additive change than enum value/removal complexity. Limitation accepted for V1.
- **Telegram bigint values can lose precision in JavaScript.** Mitigation: preserve serialized string semantics at repository/domain boundaries and add contract tests when repositories land.
- **Plan includes many tables before application use.** Counterargument: broad upfront schema can overfit. Accepted because plan utama already fixes cross-table audit/job/session contracts; implementation should still avoid speculative columns not listed here.

- Keputusan lease: `p_lease_seconds integer` bounded (1..86400, default 300) dipakai untuk validasi RPC lebih jelas daripada `interval`.
- Supabase auto-grant EXECUTE ke `anon`/`authenticated` untuk function baru di schema yang ter-expose; revoke dari `public` saja tidak cukup → migration ke-4 revoke explicit dari `public, anon, authenticated` lalu grant `service_role` saja.
- Host DB untuk test: `aws-0-<region>.pooler.supabase.com` (port 6543, user `postgres.<ref>`). Region di-derive dari Management API memakai `SUPABASE_ACCESS_TOKEN` saat runtime.
- Vitest: `fileParallelism: false` karena claim job antar test file saling rebut job fixture bila berjalan paralel.
